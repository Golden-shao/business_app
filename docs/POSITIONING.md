# 产品方向：使用者获得工具，维护者学习 K8s

根据 2026-10-25 的产品要求调整：首要使用者是需要连接模型的小团队和个人应用开发者。K8s 是交付与可靠性实现方式，不要求普通使用者先学习 Kubernetes。

## 不宣称“全世界没人做过”

可核实的已有产品包括 [LiteLLM](https://docs.litellm.ai/docs/simple_proxy) 的多供应商代理、配额、日志和路由，以及 [Portkey Gateway](https://github.com/Portkey-AI/gateway) 的开源多模型网关。仅做转发、限流、缓存和仪表盘不足以证明创新。这里是有限范围调研，不是完整竞品扫描或全球首创证明。

## 下一步需要验证的差异化假设

**面向独立开发者的移动优先模型连接与故障恢复台**：接入一个自托管实例，在网页与手机上看到同一条请求、定位失败、明确何时可以重试，并在分享诊断时不暴露消息和供应商密钥。

当前已有跨端状态、来源与请求 ID、限流提示、共享状态和模拟模式。后续候选是可导出的脱敏诊断包、可验证的接入向导、可撤销设备凭证。它们是待用户验证的假设，不是已实现功能或独有性声明。

## 两条验收路径

| 角色 | 验收问题 |
| --- | --- |
| 使用者 | 能否通过一个 HTTPS 地址连接实例，成功调用 API，失败时知道下一步，而无需接触 kubectl？ |
| 实例维护者 | 能否用固定镜像和部署配置复现运行，完成证书、备份、滚动更新、观测和恢复？ |
| 社区贡献者 | 能否不提供真实模型 Key 就运行测试、提交 PR，并获得可追溯的独立审查？ |

先让 3 位目标使用者分别完成接入与一次故障恢复，记录失败位置，再决定是否投入诊断包/设备授权。还没有这些访谈或使用数据，不提前承诺收入、用户规模或社区活跃度。
